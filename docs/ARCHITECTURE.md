# System Architecture & Technical Design

This document details the hardware-software co-design of the **Tetris Arcade System** running on the **AGM AG32VF407 / AG32VH407** SoC.

---

## 1. System Overview

The AGM AG32 is a heterogeneous SoC that encapsulates three primary components within a single LQFP-64 package:
1. **RISC-V 32-bit RV32IMAFCB MCU**: Running at 150 MHz with 128 KB SRAM and 256 KB on-chip Flash.
2. **Alta-Gate CPLD/FPGA Matrix (~2K Logic Elements)**: User-programmable logic embedded directly on the bus.
3. **8 MB System-in-Package (SiP) HyperRAM**: Connected via a dedicated high-speed HyperBus interface running at 150 MHz.

## 2. Memory Map & Address Space

| Base Address | Size | Memory Type | Usage |
|---|---|---|---|
| `0x20000000` | 128 KB | Internal SRAM | Stack, Heap, Game State Variables |
| `0x80000000` | ~208 KB | Internal Flash (Bank 0) | RISC-V Program Firmware (`hmi_app.bin`) |
| `0x80034000` | ~48 KB | Internal Flash (Bank 1) | CPLD Configuration Bitstream (`rgb.bin`) |
| `0x60000000` | 8 MB | SiP HyperRAM | Framebuffer: 800 × 480 × 2 bytes = 768,000 bytes |
| `0x70000000` | — | AHB Peripheral Space | CPLD RGB DMA Control Registers |
| External SPI | 2 MB | W25Q16JV Flash | Splash screens, persistent assets |

## 3. Zero-CPU Video Refresh Pipeline

Driving an $800 \times 480$ 16-bit RGB display at 60 FPS requires a continuous bandwidth of:
$$800 \times 480 \times 2\text{ bytes} \times 60\text{ FPS} \approx 46.08\text{ MB/s}$$

A standard MCU cannot maintain this throughput via software bit-banging without starving the CPU. In this project:
1. **HyperRAM DMA**: The CPLD contains an internal DMA engine connected directly to the HyperRAM controller.
2. **Circular Burst Mode**: The DMA controller is configured to continuously read 12,000 chunks of 64 bytes (`LCD_DMA_FRAME_CHUNKS = 800 * 480 * 2 / 64 = 12000`) in a continuous loop.
3. **Dual-Clock FIFO**: Data fetched from HyperRAM is pushed into a 64-byte asynchronous FIFO (`fifo2rgb.v`).
4. **Display Synchronization**: The read side of the FIFO is clocked by the 25 MHz pixel clock (`DCLK`) generated by a divider from the system clock (`DCLK_DIV = 6`). The timing generator asserts `HSYNC`, `VSYNC`, and `DE` strictly conforming to ST7262 specifications.
5. **Zero CPU Overhead**: The CPU only writes updated pixel colors into HyperRAM (`0x60000000`). Once written, the hardware pipeline refreshes the screen autonomously.

## 4. Portrait Transformation & Gate-Driver Artifact Mitigation

### 4.1. Coordinate Transformation
The LCD panel is physically mounted in landscape ($800 \times 480$). To display Tetris in vertical portrait ($480 \times 800$) oriented $180^\circ$ counter-clockwise:
$$\begin{cases}
px = y \\
py = 479 - x
\end{cases}$$
where $(x, y)$ are the logical portrait coordinates ($x \in [0, 479], y \in [0, 799]$) and $(px, py)$ are the physical panel coordinates ($px \in [0, 799], py \in [0, 479]$).

### 4.2. Physical Gate-Driver Settling Noise (The 56 px Safe Margin)
During initial bring-up, high-frequency rendering on the portrait left margin ($x < 40$) produced severe vertical smearing that clipped the letter 'T' of the title and distorted HUD borders.
* **Root Cause Analysis**: The mapping $py = 479 - x$ dictates that portrait coordinates $x = 0 \dots 40$ map directly to physical panel rows $py = 440 \dots 479$. Physical rows 440..479 sit immediately adjacent to the flexible printed circuit (FPC) bonding area and the internal gate-driver shift registers of the ST7262 IC. Rapid color transitions near these rows caused gate-line capacitive loading and settling noise.
* **The Solution**: An engineered **56-pixel Safe Margin** was established on both lateral borders ($X \in [56, 424]$). All UI elements, fonts, borders, and the $360 \times 560\text{ px}$ playfield operate strictly inside this clean scan zone ($py \le 423$), completely eliminating 100% of the display noise.

## 5. Input Subsystem & Debouncing

Mechanical tactile switches bounce rapidly for $5 \dots 20\text{ ms}$ upon contact make and break. Traditional delay-based debounce algorithms introduce an unacceptable $20\text{ ms}$ lag in high-speed arcade gaming.

### 5.1. Instant Leading-Edge Lockout Algorithm
1. **Leading Edge (Press)**: When the switch first makes contact, `raw_pressed && !curr_pressed` triggers in the first microsecond ($0\text{ ms}$ latency). The event flag is dispatched immediately to the game engine.
2. **Lockout Interval (35 ms)**: The algorithm records `s_last_press_time[i] = now`. For the subsequent 35 ms, all mechanical contact vibrations are ignored.
3. **Trailing Edge (Release)**: Symmetrical 35 ms lockout ensures release bounce does not re-trigger a spurious press.

### 5.2. Auto-Polarity Baseline Detection
At system boot in `board_hw_init()`:
```c
s_idle_state = GPIO_GetValue(BTN_GPIO, BTN_ALL_BITS);
```
During runtime:
```c
uint8_t changed = (val ^ s_idle_state) & BTN_ALL_BITS;
```
By utilizing bitwise XOR against the boot baseline, the system automatically accepts:
* **Active-Low buttons** (pulled up internally to 3.3V, pressed to GND).
* **Active-High buttons** (pulled down externally to GND, pressed to 3.3V).
